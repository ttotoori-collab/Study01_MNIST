# 손글씨 숫자 인식기 — 웹/데스크톱 분리 설계

작성일: 2026-09-24

## 1. 목적

하나의 폴더에 섞여 있는 MNIST 손글씨 인식 코드를 두 개의 독립된 버전으로 나눈다.

- **desktop_version** — 기존 PyTorch + tkinter 앱. 코드를 그대로 옮기고 경로만 정리한다.
- **web_version** — 새로 작성한다. 외부 라이브러리 없이 순수 자바스크립트로 추론하며
  GitHub Pages에 정적으로 배포된다.

두 버전은 같은 전처리 알고리즘을 공유하지만 모델 가중치와 실행 환경은 분리된다.

## 2. 수용 기준

| 항목 | 기준 |
| --- | --- |
| 웹 모델 MNIST 테스트 정확도 | 99.0% 이상 |
| 가혹 손글씨 시뮬레이션 정확도 | 98.5% 이상 |
| JS 추론과 PyTorch 로짓 최대 오차 | 1e-4 이하 |
| 전처리 결과(28x28) Python vs JS 최대 오차 | 1e-3 이하 |
| `weights.bin` 크기 | 500KB 이하 |
| 웹 추론 지연 | 획을 뗀 뒤 50ms 이내 |
| 런타임 외부 의존성 | 0개 (빌드 단계 없음) |

채점 조건은 "0~9를 여러 형태로 50번 그려 49번 이상 정답"이다. 50회 중 1회 오답까지
허용되므로, MNIST 테스트 정확도만으로는 부족하다고 보고 가혹 시뮬레이션 기준을
98.5%로 따로 둔다.

### 근거가 된 사전 측정

현재 데스크톱 모델(MNIST 테스트 99.19%)을 실제 앱 전처리 경로에 통과시켜 측정한 결과다.

| 조건 | 정확도 |
| --- | --- |
| MNIST 테스트 이미지를 캔버스 크기로 되돌린 것 | 99.0% (198/200) |
| 손글씨 글꼴 렌더링 (회전/크기/위치 변화) | 100% (210/210) |
| 위 + 손떨림·획 굵기·기울기 왜곡 | **97.5% (390/400)** |

가장 가혹한 조건에서 97.5%였고 오답은 1→2 혼동에 몰려 있었다. 이 격차를 메우기 위해
아래 두 가지를 설계에 포함한다.

- **학습 시 어파인 증강** — 회전 15도, 이동 12%, 확대축소 0.8~1.2, 전단 12도, 획 굵기 변화
- **글꼴 숫자 혼합 학습** — 글꼴로 그린 숫자 20,000장을 실제 전처리까지 통과시켜
  MNIST에 25% 비중으로 섞는다
- **추론 시 TTA** — 원본과 상하좌우 1px 이동, 5회 예측의 확률 평균

### 글꼴 숫자를 섞는 이유 (구현 중 측정으로 확인)

증강만으로 학습한 1차 모델은 MNIST 99.29%를 얻고도 가혹 벤치마크에서 94.5%에
그쳤다. 오답 22건 중 11건이 1을 2로 읽은 것이었다. 왜곡을 하나씩 꺼 가며 측정한
결과 어떤 왜곡을 꺼도 이 혼동이 남았고, 왜곡을 전부 끄고 숫자 1만 그려도
Segoe Script Bold의 '1'을 '2'로 예측했다.

원인은 글자꼴이다. 숫자 1의 세로/가로비가 Comic·Inkfree 계열은 2.1~2.4인 반면
Segoe Script·Print 계열은 1.09~1.13으로, 밑변 세리프와 큰 깃발이 달린 넓적한
형태다. MNIST에는 이 형태가 없어 학습으로 메워지지 않는다. 에폭을 늘리는 것은
해결책이 아니다.

따라서 글꼴로 그린 숫자를 학습에 섞되, **학습 글꼴 19종과 벤치마크 글꼴 5종을
서로 겹치지 않게** 나눈다. 벤치마크가 학습에서 본 적 없는 글자꼴에 대한 일반화를
재는 독립적인 잣대로 남아야 하기 때문이다.

## 4. 웹 전용 경량 모델

데스크톱 모델은 FC 한 층이 전체 파라미터의 98%를 차지해 4.8MB가 된다. 웹에서는
풀링을 한 번 더 넣어 FC 입력을 9216에서 1568로 줄인다.

```
입력 (1, 28, 28)
 -> Conv2d(1, 16, 3, padding=1) + ReLU     (16, 28, 28)
 -> MaxPool2d(2)                           (16, 14, 14)
 -> Conv2d(16, 32, 3, padding=1) + ReLU    (32, 14, 14)
 -> MaxPool2d(2)                           (32, 7, 7)
 -> Flatten                                (1568,)
 -> Linear(1568, 64) + ReLU
 -> Dropout(0.3)
 -> Linear(64, 10) -> LogSoftmax
```

| | 데스크톱 | 웹 |
| --- | --- | --- |
| 파라미터 | 1,199,882 | 105,866 |
| float32 크기 | 4.8MB | 414KB |
| 추론 연산량 | 약 1,200만 MAC | 약 110만 MAC |

학습: Adadelta(lr=1.0), StepLR(gamma=0.7), 배치 128, 15에폭, 위의 어파인 증강 적용.
테스트셋 최고 정확도 시점의 가중치를 저장한다.

## 5. 가중치 포맷

`model/weights.bin` — 리틀엔디언 float32를 레이어 순서대로 이어 붙인 한 덩어리.

`model/weights.json` — 메타데이터.

```json
{
  "구조": "web-cnn-v1",
  "정규화": { "평균": 0.1307, "표준편차": 0.3081 },
  "레이어": [
    { "이름": "conv1.weight", "형태": [16, 1, 3, 3], "오프셋": 0, "개수": 144 },
    { "이름": "conv1.bias",   "형태": [16],          "오프셋": 144, "개수": 16 }
  ]
}
```

레이어 순서는 `conv1.weight`, `conv1.bias`, `conv2.weight`, `conv2.bias`,
`fc1.weight`, `fc1.bias`, `fc2.weight`, `fc2.bias` 여덟 개이며 위와 같은 형식으로
이어진다. 이 순서가 곧 `weights.bin`의 배치 순서다.

JS는 `weights.json`을 읽어 `ArrayBuffer` 위에 `Float32Array` 부분 뷰를 만든다. 복사가
없어 메모리와 시작 시간 모두 절약된다.

`file://`로 열면 `fetch`가 차단되므로, 로더는 이 경우를 감지해 "정적 서버로 열어
주세요"라는 안내와 명령 한 줄을 화면에 표시한다.

## 6. 순수 JS 추론 엔진

**`js/nn.js`** — 외부 의존성 없는 텐서 연산. 모든 데이터는 `Float32Array`이고
형태는 `[채널, 높이, 너비]` 순서로 다룬다.

| 함수 | 역할 |
| --- | --- |
| `conv2d(입력, 가중치, 편향, 설정)` | padding 지원 2차원 합성곱 |
| `relu(입력)` | 제자리 ReLU |
| `maxPool2d(입력, 크기)` | 2x2 스트라이드 2 최대 풀링 |
| `linear(입력, 가중치, 편향)` | 완전연결 |
| `softmax(로짓)` | 확률 변환 (최댓값 빼기로 수치 안정화) |

**`js/model.js`** — 가중치를 로드하고 위 연산을 순서대로 엮는다. `예측(입력28x28)`은
TTA 5회를 평균한 확률 배열 10개를 반환한다.

연산량이 TTA를 포함해도 약 550만 MAC이므로 일반 노트북에서 10ms 이내로 끝난다.
워커나 WASM 없이 메인 스레드에서 처리한다.

## 7. 전처리 동등성

`js/preprocess.js`는 데스크톱 `app.py`의 `이미지_전처리()`를 그대로 옮긴다.

1. 캔버스 픽셀을 읽어 흑백 반전 (배경 0, 획 255)
2. 값이 20을 넘는 영역의 경계 상자로 잘라내기
3. 가로세로 비율을 유지하며 긴 변을 20px로 축소
4. 28x28 한가운데 배치
5. 픽셀 무게중심을 (13.5, 13.5)로 평행 이동
6. `(값 / 255 - 0.1307) / 0.3081`

3번의 축소 필터만 다르다. PIL은 LANCZOS를 쓰지만 JS는 **면적 평균(area average)**을
직접 구현한다. 캔버스 `drawImage`의 보간은 브라우저마다 결과가 달라 재현이 되지
않기 때문이다. 이 차이는 테스트로 수치를 확인하고 허용 오차 안에 드는지 검증한다.

## 8. 화면

좌: 280x280 캔버스 (마우스·터치), `지우기` 버튼.
우: 예측 숫자(대형), 확신도, 0~9 확률 막대, **모델 입력 28x28 미리보기**(확대 표시).

획을 뗄 때마다 자동으로 인식한다. 좁은 화면에서는 세로로 쌓인다. 색상과 배치는
데스크톱 앱과 맞춘다.

## 9. 테스트 전략

| 테스트 | 실행 | 검증 내용 |
| --- | --- | --- |
| 내보내기 검증 | `tools/export_weights.py` | 저장한 bin을 numpy로 되읽어 PyTorch 출력과 일치 |
| JS 추론 동등성 | `node tests/run.mjs` | MNIST 20장 로짓을 PyTorch 결과와 비교, 오차 1e-4 |
| 전처리 동등성 | `node tests/run.mjs` | 같은 입력의 28x28 배열 비교, 오차 1e-3 |
| 가혹 벤치마크 | `tools/bench.py` | 손떨림·굵기·기울기 왜곡 400장에서 98.5% 이상 |

fixture는 `tools/make_fixtures.py`가 생성해 `tests/fixtures.json`에 저장한다.
node v24가 설치되어 있어 브라우저 없이 실행된다.

## 10. 배포

`.github/workflows/pages.yml`은 `main` push 시 `web_version/`에서 `tools/`와 `tests/`를
제외한 내용을 staging 폴더로 복사해 Pages 아티팩트로 올린다. 사이트 루트가 곧
`index.html`이 되므로 모든 경로는 상대경로로 작성한다.

## 11. CLAUDE.md 구성

- **루트** — 두 폴더의 역할, 작업 전 어느 쪽인지 확인, 공통 규칙(모든 코드와 주석은 한글)
- **desktop_version** — 파이썬 실행 경로, 학습/실행 명령, 바탕 화면 바로가기, 가중치 파일 위치
- **web_version** — 외부 라이브러리 금지, 가중치 재생성 절차, 테스트 실행법, Pages 배포 방식

## 12. 이동에 따른 뒷정리

- 바탕 화면 바로가기의 대상과 시작 위치를 `desktop_version/`으로 갱신한다. 하지 않으면 깨진다.
- `.gitignore`에 `data/`, `__pycache__/`, `*.pt`를 넣는다. 단 `web_version/model/weights.bin`은
  배포에 필요하므로 커밋 대상이다.
- `.py` 파일 연결(`py.exe`)은 경로와 무관하므로 영향이 없다.
